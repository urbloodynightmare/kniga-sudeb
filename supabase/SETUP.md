# Подключение личных аккаунтов

Фронтенд размещается на GitHub Pages. Supabase хранит личные листы и управляет входом.

1. Войдите в https://supabase.com/dashboard и создайте проект. Пароль базы данных остаётся у вас и не нужен сайту.
2. В SQL Editor выполните содержимое `schema.sql` из этой папки. Скрипт включает приватный доступ: игрок читает и изменяет только свою книгу. Проверка версии защищает от тихого перезаписывания другим устройством.
3. В Authentication → URL Configuration укажите адрес сайта как Site URL и Redirect URL: `https://urbloodynightmare.github.io/kniga-sudeb/`.
4. В Authentication → Providers оставьте Email включённым. По умолчанию игрок подтверждает адрес по письму. Для надёжной доставки писем настройте свой SMTP согласно рекомендациям Supabase.
5. В Connect / API Keys скопируйте Project URL и **publishable key** (`sb_publishable_…`; также поддерживается прежний `anon` key).
6. Запишите только эти публичные параметры в `app/cloud-config.js`, затем опубликуйте коммит. Никогда не используйте `service_role` или `sb_secret` ключ во фронтенде.
7. Проверьте двумя отдельными аккаунтами: создайте героя в первом, убедитесь, что во втором пустая книга; создайте второго героя и проверьте повторный вход в первый. Нужна также проверка отказа чтения чужой строки напрямую через API.

После включения облака новые аккаунты получают пустую личную книгу и выбирают заготовку своего героя. Пять персонажей не копируются автоматически во все аккаунты. Импорт старых локальных листов выполняется пользователем через файл.

До подключения конфигурации работает локальная версия для проверки интерфейса. Она явно обозначена как локальная и не изображает рабочий вход.

## Проверки

`node scripts/build-cloud.mjs` пересобирает локальный бандл официального Supabase SDK после обновления зависимости.

`node --test tests/*.test.mjs` проверяет игровой движок и последовательность облачного сохранения с конфликтами. Эти тесты не заменяют проверку реальных RLS-политик на подключённом проекте.

## Комнаты партии

После основной схемы выполните `rooms.sql`, затем `room-management.sql` (он также подключает ограниченные сводки мастера). Он добавляет комнаты, участников, общий дневник и историю записей; личные книги остаются приватными. В SQL Editor можно выполнить `rooms-check.sql`: проверки создают временные аккаунты внутри транзакции и откатывают все тестовые изменения.

Создатель комнаты становится единственным мастером. Мастер и создатель могут передать роль участнику, заменить приглашение и исключить игрока. Вход по приглашению открывает текущему мастеру просмотр компактной игровой сводки выбранного для комнаты героя. Полный лист и личные записи не передаются. RPC просмотра проверяет роль на сервере; редактирование чужих книг не разрешается. Игроки видят общие записи и список участников.

Общие записи сохраняются отдельно от личной книги через `save_party_note` с проверкой версии. Каждое сохранение добавляется в историю. При конфликте текст остаётся в локальном черновике, который можно сохранить отдельной записью. Записи убираются в обратимый архив. Supabase Realtime обновляет записи; опрос раз в 12 секунд страхует пропущенные события и обновляет карточки мастера. Черновики на устройстве изолированы по аккаунту, комнате и записи.

Для проверки выбора персонажа, удаления комнаты и личных копий дневника выполните `room-management-check.sql`. Он работает в транзакции с полным откатом тестовых данных. Удалять комнату может её создатель. Комната исключается из активных, приглашение отключается; записи и история копируются каждому участнику в отдельную таблицу `room_diary_archives` с доступом только владельцу. Старое автосохранение книги не может стереть эти копии. Состояния сворачивания разделов и карточек сохраняются на устройстве отдельно для каждой комнаты.

## Торговцы комнаты

После схемы комнат выполните `merchants.sql`. `merchants-check.sql` проверяет реальные права доступа и RPC внутри транзакции с откатом. Только текущий мастер может импортировать, изменять, публиковать и удалять торговцев. RLS скрывает неопубликованных торговцев даже при прямом запросе игрока к таблице; участники других комнат не видят каталог. При передаче роли права переходят новому мастеру. Проверка версии не допускает тихой перезаписи из старого окна.

Вкладка «Торговцы» принимает DOCX, JSON, CSV/TSV и текст/Markdown. В Word распознаются таблицы с колонками «Товар» и «Цена», имя и место берутся из заголовка перед таблицей. «Имя — Место», двойной пробел и отдельные поля «Имя:» / «Место:» поддерживаются. В JSON нужен массив `merchants` с полями `name`, `location`, `items: [{name, price}]`; образец скачивается из окна импорта. CSV использует столбцы «Торговец;Место;Товар;Цена»; файл может быть в UTF-8 или Windows-1251. Дополнительные столбцы, экономические рекомендации и сюжетный текст пропускаются. Диапазоны цен и текстовые цены сохраняются дословно. Отсутствующее место не выдумывается: его можно дописать в предпросмотре.

Файлы разбираются в браузере; в базу отправляются только проверенные имя, место и пары товар/цена, без исходного документа. Новые торговцы скрыты по умолчанию. Повторный импорт совпадающего имени и места обновляет ассортимент без дублирования и сохраняет текущую видимость. Весь импорт атомарен. Между игроками каталог обновляется при открытии вкладки, вручную и при опросе комнаты раз в 12 секунд. DOCX ограничен 10 МБ, распаковывается только текст документа размером до 5 МБ; картинки и внешние ресурсы не загружаются. Текстовый импорт — до 1 МБ, один импорт — до 100 торговцев, по 500 товаров на каждого; сервер также ограничивает размер запроса.

`node scripts/build-docx.mjs` пересобирает локальный Word-импортёр с библиотекой fflate. После изменения парсера обновите версию его URL в исходнике импорта и пересоберите бандл.

Импорт Word читает определения стилей из `word/styles.xml`, включая числовые и пользовательские идентификаторы, наследование и уровни структуры. Таблицы внутри элементов управления содержимым также обрабатываются. Колонки «Наименование», «Услуга», «Базовая цена», «Стоимость» и цены с уточнениями распознаются; заголовок таблицы ищется среди первых десяти строк. При нескольких ценовых колонках в предпросмотре можно выбрать нужную для каждого торговца. По умолчанию выбирается небазовая колонка цены продажи, если она есть. При текстовом списке в Word используются явные поля «Имя:» / «Торговец:», «Место:» и пары «Предмет — цена» или «Предмет: цена» с валютой. Исходные диапазоны и составные цены сохраняются, автоматического пересчёта репутации нет.

## Боевые сцены

После `merchants.sql` выполните `combat.sql`: он использует серверную проверку `is_party_master`. `combat-check.sql` проверяет приватность, права записи, смену мастера, отдельные копии участников, переименование карточки пула и конфликты версии. Проверки выполняются с полным откатом временных аккаунтов и комнат.

Мастер импортирует пул противников для комнаты из DOCX, JSON или текстовых статблоков и проверяет значения перед сохранением. DOCX использует общий разборщик стилей и таблиц. Таблицы «Поле — Значение», блоки с ХП/КД и отдельные текстовые поля поддерживаются; действия, реакции, особенности, сопротивления и остальные исходные сведения сохраняются. Неопознанные показатели не заменяются выдуманными числами: хиты и КД необходимо заполнить в предпросмотре. Максимум 200 карточек за импорт, файл до 10 МБ. В JSON допустим массив или `{monsters:[...]}` с `name`, `hpMax`, `ac`, `initiative`, `speed`, `abilities:{str,dex,con,int,wis,cha}`, `features:[{name,body}]`, `raw`; также поддерживаются распространённые поля `hit_points`, `armor_class` и полные английские названия характеристик. Предпросмотр сохраняет неизвестные поля в исходной карточке. Пул редактируется вручную, повторный импорт того же имени обновляет шаблон.

Для сцены мастер выбирает число копий монстров и выбранные героями карточки комнаты. Каждая копия получает собственный идентификатор и снимок характеристик. Изменение шаблона или удаление его из пула не изменяет существующие копии. Сцена допускает до 100 участников. Доступны ручная инициатива, бросок инициативы для всех, начало/пауза, следующий ход с переходом раунда, урон/лечение и ручное редактирование характеристик и способностей участника. Хиты ограничены диапазоном 0…максимум. Игровые показатели героя в сцене являются снимком, изменения не перезаписывают личный лист игрока.

`party_monsters` и `party_combat` читаются только мастером через RLS. Игроки получают `party_combat_view` с явным списком публичных полей: название сцены, раунд, признак активности, текущий участник, имена и инициатива в порядке хода. Хиты, КД, характеристики, способности, источники и личные данные в этот ответ не входят. Realtime подписывает игроков только на `party_combat_updates`, содержащую идентификатор комнаты и номер версии; после сигнала клиент загружает разрешённое представление. Опрос комнаты раз в 12 секунд страхует пропуски. Все изменения сцены проверяют роль мастера и ожидаемую версию на сервере.
