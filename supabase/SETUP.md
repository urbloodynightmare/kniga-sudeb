# Подключение личных аккаунтов

Фронтенд размещается на GitHub Pages. Supabase хранит личные листы и управляет входом.

1. Войдите в https://supabase.com/dashboard и создайте проект. Пароль базы данных остаётся у вас и не нужен сайту.
2. В SQL Editor выполните содержимое `schema.sql` из этой папки. Скрипт включает приватный доступ: игрок читает и изменяет только свою книгу. Проверка версии защищает от тихого перезаписывания другим устройством.
3. В Authentication → URL Configuration укажите адрес сайта как Site URL и Redirect URL: `https://urbloodynightmare.github.io/kniga-sudeb/`.
4. В Authentication → Providers оставьте Email включённым. По умолчанию игрок подтверждает адрес по письму. Для надёжной доставки писем настройте свой SMTP согласно рекомендациям Supabase.
5. В Connect / API Keys скопируйте Project URL и **publishable key** (`sb_publishable_…`; также поддерживается прежний `anon` key).
6. Запишите только эти публичные параметры в `app/cloud-config.js`, затем опубликуйте коммит. Никогда не используйте `service_role` или `sb_secret` ключ во фронтенде.
7. Проверьте двумя отдельными аккаунтами: создайте героя в первом, убедитесь, что во втором пустая книга; создайте второго героя и проверьте повторный вход в первый. Нужна также проверка отказа чтения чужой строки напрямую через API.

После включения облака новые аккаунты получают пустую личную книгу и выбирают заготовку своего героя. Пять персонажей не копируются автоматически во все аккаунты. Импорт старых локальных листов выполняется пользователем через файл.

До подключения конфигурации работает локальная версия для проверки интерфейса. Она явно обозначена как локальная и не изображает рабочий вход.

## Проверки

`node scripts/build-cloud.mjs` пересобирает локальный бандл официального Supabase SDK после обновления зависимости.

`node --test tests/*.test.mjs` проверяет игровой движок и последовательность облачного сохранения с конфликтами. Эти тесты не заменяют проверку реальных RLS-политик на подключённом проекте.
